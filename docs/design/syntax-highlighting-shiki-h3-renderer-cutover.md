# Nuvyn Shiki H3 — Markdown Renderer Cutover

> H3 changes only the normal Markdown fenced-code renderer. It does not
> activate class-based Shiki CSS, change theme selectors, or change PDF code
> styling. H4-H6 remain required before the migration can be released.

## 2. Renderer before/after

The H2 renderer contract was:

```text
MarkdownIt fence callback
    ↓
highlight.js or escaped hljs fallback
    ↓
DOMPurify
```

H3 now uses:

```text
raw Markdown
    ↓
md.parse(markdown, isolated discovery env)
    ↓
discover actual fence tokens
    ↓
await prepareShikiLanguages()
    ↓
md.render(markdown, fresh real render env)
    ↓
sync MarkdownIt fence callback
    ├─ exact markmap → .markmap-mount placeholder
    ├─ exact mermaid → .mermaid-mount placeholder
    ├─ ready canonical Shiki language → highlighter.codeToHtml()
    └─ unknown/empty/unavailable/error → escaped plain fallback
    ↓
DOMPurify
    ↓
Vue v-html consumers
```

`render(markdown, options): Promise<string>` remains unchanged. H2 still owns
the asynchronous runtime and grammar preparation; H3 only consumes the ready
runtime synchronously during `md.render()`.

## 3. Synchronous Shiki callback

`src/lib/shiki.ts` now exposes the narrow synchronous helper:

```text
highlightShikiFence(source, info): string | null
```

The helper:

- resolves the fence through the existing H2 `extractFenceLanguageIdentifier()`
  and `resolveShikiLanguage()` helpers;
- reads only the already-active singleton highlighter and canonical loaded set;
- calls `codeToHtml()` synchronously with `github-light` and `github-dark` plus
  `defaultColor: false`;
- never calls `getShikiRuntime()`, `loadLanguage()` or a dynamic import;
- returns `null` when the runtime/grammar is not ready or one `codeToHtml()` call
  throws, allowing the Markdown fence callback to use the safe fallback.

The callback returns HTML, never a Promise. Runtime initialization remains
outside this boundary and therefore still rejects the async `render()` call.

## 4. Canonical language contract

The callback does not normalize language identifiers independently. Metadata is
removed by the shared first-info-token helper before the exact special-fence
checks and the same canonical Shiki resolver used by H2 is then reused.

Examples covered by H2/H3 evidence include:

```text
js / javascript   → javascript
ts / typescript   → typescript
py / python       → python
yml / yaml        → yaml
```

`title=demo`, `linenums` and other fence metadata are not passed to Shiki as a
language identifier. User input is never used as a module path or generated
class name.

## 5. Known-language HTML contract

Representative JavaScript, TypeScript, Java, SQL and Python fences now produce
sanitized structural Shiki HTML:

```html
<pre class="shiki shiki-themes github-light github-dark">
  <code>
    <span class="line">…</span>
  </code>
</pre>
```

The actual Shiki token spans are generated by `codeToHtml()`; H3 does not
manually synthesize token markup. DOMPurify preserves `pre.shiki`, `code`,
`span.line` and text, while removing Shiki's inline `style` attributes under
the existing sanitizer policy.

Normal Nuvyn fenced output no longer uses `class="hljs"` or the highlight.js
callback. Exact token classes and final colors are intentionally not an H3
contract; H4/H5 own that work.

## 6. Unknown and empty fallback

Unknown language, empty language, unavailable grammar and a not-ready runtime
inside the synchronous callback all use the fixed escaped fallback:

```html
<pre class="shiki nuvyn-shiki-plain"><code>escaped source</code></pre>
```

The source is escaped through the existing centralized HTML escaping logic.
It remains readable text, cannot create an element from `<world>` or `<b>`,
does not initialize Shiki for unknown/empty fences, and does not use the old
`hljs` class.

## 7. Grammar-load failure fallback

H2's known-grammar failure semantics remain per-language and retryable. After
the H3 cutover, an `unavailable` preparation result maps to plain code instead
of falling back to the old renderer:

```text
JavaScript grammar loaded → Shiki structural HTML
Python grammar unavailable → nuvyn-shiki-plain escaped fallback
whole document → resolves
singleton → remains healthy
later preparation → may retry Python
```

The integration regression proves that a successful fence in the same
document still uses Shiki while the failed fence falls back independently.

## 8. `codeToHtml()` failure fallback

`highlightShikiFence()` catches only the synchronous failure for the current
fence and returns fallback-required. It does not catch the whole Markdown
render, replace the document with raw Markdown, recreate the highlighter, or
change loaded-language state. A later fence and later render can still use the
same runtime.

## 9. Runtime initialization failure contract

The H2 follow-up distinction remains intact:

```text
createHighlighter()/getShikiRuntime() failure → render rejects
rejected singleton promise                 → cleared for retry
language in-flight entry                   → cleaned on rejection
next render                                → may initialize a new runtime
```

This is different from grammar load failure and different from a per-fence
`codeToHtml()` failure. The Markdown integration regression confirms the first
render rejects and the next render succeeds with `pre.shiki` output.

## 10. MarkMap / Mermaid preservation

Exact special identifiers are checked before Shiki resolution:

```text
markmap → .markmap-mount + encoded data-content
mermaid → .mermaid-mount + encoded data-content
```

No Shiki runtime or grammar is prepared for a document containing only these
special fences. Their mount code, `data-content`, `encodeURIComponent()`
transport and PDF staticization were not changed. Similar names (`mmap`,
`merm`, `mark-map`, `mer-maid`) remain normal unsupported/plain fences, and
case-sensitive boundaries such as `MARKMAP` remain non-special.

## 11. Sanitizer behavior

The Markdown sanitizer configuration was not changed:

```ts
FORBID_ATTR: ['style']
```

H3 evidence proves that:

- sanitized known Shiki output retains `pre.shiki`, `code` and `span.line`;
- Shiki-generated inline `style` attributes do not survive;
- existing raw HTML/event-handler sanitizer tests remain green;
- no generated stylesheet or Shiki `<style>` element is placed in article HTML.

`transformerStyleToClass` is not passed to production `codeToHtml()` yet. The
H1 transformer instance remains available for H4, but H3 intentionally accepts
that token colors are not yet visually complete after sanitizer removal of
inline styles.

## 12. Markdown extension regressions

The existing MarkdownIt instance and plugin order remain intact. Focused and
browser regressions cover the normal application surface without changing
task lists, headings/anchors, footnotes, definition lists, `==mark==`,
WikiLinks, callouts, math, emoji, tables, Mermaid or MarkMap behavior.

## 13. Resolver regressions

H2's isolated preflight and fresh real render environment remain unchanged.
The H3 callback has no access to the resolver and does not parse Markdown or
perform asynchronous work. Resolver call-count and concurrent A/B isolation
tests remain green.

## 15. Remaining highlight.js ownership

The following are intentionally retained until H7:

```text

src/hljs-dark.css                  → present
MarkMap features.hljs contract     → present and separately owned
MarkMap transitive highlight.js     → not a Nuvyn renderer import
historical docs/comments            → retained where they describe prior phases
```

The active normal Markdown path no longer imports `highlight.js`,
`highlight.js/styles/github.css` or `src/hljs-dark.css`, and no longer calls
`hljs.highlight()`.

## 16. H3 visual limitation / H4 handoff

H3 establishes the Shiki renderer and sanitized structural HTML contract. It is
not the final syntax-color implementation.

Because H4 has not yet activated `transformerStyleToClass` in production and
no generated stylesheet owner exists, H3 intentionally does not create:

```text
style#nuvyn-shiki-generated-styles
src/shiki.css
document.head Shiki CSS owner
```

H5 still owns theme selector integration and no-rerender theme switching. H6
still owns printable light token colors and PDF computed-color proof. H3 is
therefore not a visual or release gate by itself.
